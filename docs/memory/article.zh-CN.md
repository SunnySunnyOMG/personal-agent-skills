# 你的 Agent 为什么不好用？先看看它怎么记忆

你说“可能周五出发”，智能体却一直按周五安排。它确实记住了这句话，但把一个尚未确定的计划，当成了可以持续使用的事实。

在构建个人智能体时，我越来越在意这种差别：**记下来，不等于已确认；已确认，不等于永远有效；保留着，也不等于每次都要用。**

Coding Agent 或 Agent Harness 自带的记忆，是一套默认策略，未必符合每个人的偏好。临时要求变成永久规则、旧安排继续影响回答，都可能让记忆产生负面效果。我们需要设定的，是信息在什么条件下可以影响未来的判断。

用一趟虚构的旅行，把这件事拆开看。你告诉智能体：“我可能周五去杭州，这次打车，住址别记。”这三句话不能一起塞进长期记忆：住址按意愿排除；“可能周五”连着来源保留为待确认提议；“这次打车”只属于本次行程。重复和没有长期价值的输入，也不必不断提炼成新笔记。是否保留原件，是另一个决定；密钥不应进入普通记忆。

后来，核对订单发现订的是周六，当前安排才按周六。先前的提议留在时间线里，说明判断如何改变。确认的是这份订单所支持的安排，不是永恒不变的结论。新时间戳、同一段话被重复采集、模型自己反复总结，都不能替代新证据。证据有冲突，就保留未知，别强行定案。

这就是前几层的分工：原件留依据，有来源的记录保留确认状态，事项笔记维护当前最有依据的理解。同一件事保持稳定身份，当前摘要可以更新，历史解释变化。普通纠错补上修正与替代关系，并复核依赖旧判断的摘要和报告。

再看记忆的寿命。“这次打车”在旅行结束后应停止生效；你明确说“以后尽量靠窗”，才形成长期偏好。不能从一次选择推导出永久规则。几次旅行都验证，订票前先核日期、地点再付款能避免误订，才把这套流程提炼成 skill。留下的是可复用的方法，不必把每趟旅行的细节都塞进去。

使用时也分层。问“什么时候出发”，先读当前安排；问“为什么按周六安排”，才沿索引找到原话、订单和时间线。旧记录可以放在后面，保留不等于常驻。少量稳定偏好可以默认加载，其他内容按任务检索。索引是路标，图和向量也可以是可重建的检索层；内容则适合放在自己能看懂、能修改、能带走的笔记里。隐私不能从正文删掉后，又泄露在索引标题里。

临时安排可以设置“旅行结束”这样的失效条件。接好执行工具，条件满足时才能自动停用；没有自动机制，就在使用前检查。停用意味着不再当成当前安排，是否删除原件按保留规则决定。

明确要求撤回，才进入另一条流程：先停止使用，沿来源清理这趟行程的派生信息、相关历史、索引和缓存，再处理原件并复查。失去依据的技能应停用，其中的私密内容也要清理；独立证据仍支持的通用方法可以保留。外部副本、版本历史和备份，需要分别处理并交代范围。保留纠错历史的惯例，不能成为拒绝隐私撤回的理由。

你可以这样要求自己的智能体：

> 遵循我的保留偏好，区分原话、待确认信息、证据支持的现状和可复用方法。不要把一次性要求变成永久规则。按需检索，检查时效；纠错时复核派生影响，撤回时清理可控范围，并说明未处理的部分。

分层的价值，是让每条信息都有证据、适用范围和退出条件。这套方法已整理成开源 [layered-memory skill](https://github.com/SunnySunnyOMG/personal-agent-skills/tree/main/skills/layered-memory)。规则可以交给智能体执行，偏好与边界由你设定；实际读写和自动化能力取决于所用工具。
